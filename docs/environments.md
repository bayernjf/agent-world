# 软件项目环境划分

> 不同规模/风险等级的项目用不同套数的环境。本文档按「公司类型」逐一列出，并在结尾给出 agent-world 的选择结论。

## 一、标准四套环境（中大型公司主流）

| 环境 | 中文 | 用途 | 数据来源 |
|---|---|---|---|
| **DEV** | 开发环境 | 开发人员日常调试 | 构造的假数据 |
| **TEST / SIT** | 测试环境 | QA 功能测试 | 构造的假数据 |
| **STG / Staging** | 预发布 | 硬件配置贴近生产、**脱敏生产数据**、上线前最后验证 | 脱敏后的生产数据 |
| **PROD** | 生产环境 | 真实用户使用 | 真实数据 |

## 二、不同公司的环境划分

### 1. 小公司 / 初创 —— 3 套（砍掉 STG）

```
DEV → TEST → PROD
```

> 人力/服务器成本有限，跳过预发布，测试完直接上生产。**风险更高**，但早期产品验证期够用。

### 2. 中大型公司 —— 4 套（工业标准）

```
DEV → TEST → STG → PROD
```

> 补上 STG，用脱敏生产数据做上线前最后一次验证，把「测试环境能跑通但生产跑挂」的风险挡在门外。

### 3. 大型企业 / 金融 —— 5 套甚至更多

```
DEV → SIT(集成测试) → UAT(用户验收) → STG 预发布 → PROD 生产
```

- **SIT（System Integration Testing）**：模块之间接口联调
- **UAT（User Acceptance Testing）**：产品/业务方验收，业务人员亲自操作看功能是否符合需求

> 金融、医疗、政务等监管严格、出问题代价巨大的行业用。

### 4. 额外环境（部分公司按需叠加）

- **PET / PERF 压测环境**：专门做性能压测，**不与 STG 共用**——压测产生的脏数据会污染预发布环境
- **DR 灾备环境**：生产的备份容灾，主机房挂时切换

## 三、快速总结

| 规模 | 套数 | 环境组成 |
|---|---|---|
| **最小可用** | 3 套 | DEV / TEST / PROD |
| **工业标准** | 4 套 | DEV / TEST / STG / PROD |
| **严谨大企业** | 5-6 套 | DEV / TEST / SIT / UAT / STG / PROD（+压测、灾备按需） |

## 四、agent-world 的选择结论

**结论：采用「小公司 / 初创」的 3 套方案 —— DEV / TEST / PROD。**

理由：

1. **成本敏感**：每多一套环境 = 多一台服务器 + 维护 + 数据同步成本，早期产品没必要背这个负担。
2. **但保留 TEST 隔离**：比「1 套」多一个测试环境，避免开发改动直接上生产。
3. **暂不设 STG**：早期用户量小、变更频繁，测试完直接上生产可接受。

演进节奏（按商业化里程碑）：

| 阶段 | 环境套数 | 环境 | 说明 |
|---|---|---|---|
| **M0 当前** | 1 套（DEV/TEST/PROD 合一） | 本地 Ubuntu 单机 | 早期验证，见 [runbooks/deploy-ubuntu-execution-log.md](runbooks/deploy-ubuntu-execution-log.md) |
| **M3 正式上线** | **3 套** | DEV / TEST / PROD | 正式对外，按本节结论拆分 |
| **未来规模化** | 4-5 套 | 加 STG，必要时 SIT/UAT | 触发条件：用户量 / 金额 / 监管门槛上来 |

> 一句话：**现在 1 套够用，上线后按「小公司 3 套」走，规模/监管上来再升级**——不要过早拆环境（过度设计），也不要永远单环境裸奔（没隔离）。

### 当前机器与环境对照

| 机器 | 角色 | 环境 | 部署分支 | 说明 |
|---|---|---|---|---|
| Mac（开发机） | 写代码 / 调试 / 跑测试 | **DEV** | `feature/*`（本地开发） | 本地 `pnpm dev` / `pnpm test` |
| Hasee server（Ubuntu 笔记本） | 7×24 跑真实产线、成本回采 | **准生产（TEST + PROD 合一，M0）** | **`dev`** | systemd + nginx 常驻，见 [runbooks/deploy-ubuntu-execution-log.md](runbooks/deploy-ubuntu-execution-log.md) |
| （暂无） | — | 正式 **PROD** | **`main`** | M3 上线才拆，届时上云或加隧道 |

**环境 → 分支 映射**（分支跟环境走）：

| 分支 | 给谁 | 说明 |
|---|---|---|
| `main` | 正式生产 PROD（M3 才建） | 生产稳定版，只在稳定发布时更新，**不废弃** |
| `dev` | Hasee（准生产 M0） | 最新集成代码，feature 通过 PR 合并到这里 |
| `feature/*` | Mac（DEV 本地开发） | 功能开发分支，合并进 dev 前 |

**Hasee server 的定位**（为什么叫「准生产」而不是「测试环境」）：

- 它是 M0 阶段「单机合一」的落点，同时承担两个角色：**验证部署/功能（TEST 角色）+ 积攒真实运行数据（准 PROD 角色）**。
- 数据是**真实的**——成本回采（P0）依赖的就是真实产线跑出来的真实成本。
- 但它**不是正式 PROD**：无真实外部用户、无域名/TLS、无收款、无独立灾备 SLA，用户只有你自己一个。
- 所以「准生产 / 试运行」比「测试环境」更贴切：它在为未来的正式 PROD 积累真实运行证据，但还没到对外服务那一步。
