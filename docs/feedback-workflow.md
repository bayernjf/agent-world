# Feedback Workflow（用户与 Codex 沟通效率指南）

> 本文档讲"owner 怎么最快把迭代中的问题反馈给我"——**不是**产品功能。
> 产品方向上的"反馈节点"在 [PRD.md](PRD.md) 和 [docs/product-vision-discussion.md](docs/product-vision-discussion.md)。

## 一句话原则

> **截图 + 6 字标签 > 千言万语**。看到不爽就拍，标签越短越好。

---

## 4 个最快反馈方法（按成本排）

### 1. 截图 + 6 字标签（最稳）
```
[截图]
"popover 视觉脱节"
```
- ✅ 6 字标签足够，**不写描述**
- ✅ 我看到图会自己定位代码、看 token、写修复
- ⚠️ 描述细节往往跑偏（你 100 字说不清的 z-index/positioning，我一眼看懂）

### 2. 一次拍多张（批量最高效）
```
[图1: toolbar]    "下拉没对齐"
[图2: inspector]  "字段没显示"
[图3: timeline]   "回放条位置错"
```
- ✅ 我一次会话看 5-10 张图，**统一出 5-10 个 commit**
- ✅ 比你一次反馈一个快 5 倍

### 3. Codex `computer-use`（零输入）
你说 `用 computer use 看一下 toolbar`，我直接开你的 Chrome 操作、点按钮、复现 bug、截图。**你不用截图、不用描述、就坐着看**。

适合：
- bug 复现路径你不确定 → 我自己点几下找路径
- 想看 UI 实际渲染 → 我截当前状态给你
- 想让我 A/B 两种方案 → 我一边点一边改一边对比

### 4. Codex 精准指（已经在用）
- **`:codex-annotation{index="N"}`** — 在我回复里精准指某段
- **`::code-comment{...}`** — 让我把意见 attach 到代码某行

比"你上面写的那段"精准 100%。

## 防丢反馈（你的痛点）

**问题**：今天反馈的 bug 改到一半被打断，明天忘了。

**3 选 1，最轻的是第 3 个**：

### A. 反馈 md 文件进 git
本地 `feedback/20260828-01-popover.md`，commit。下次会话我 `git status` 自动看到。

### B. `feedback/pending.md` 清单
仓库根维护一份 todo 列表，commit 进 git。我每次启动扫一眼。

### C. 我自动记到 handoff.md（**最轻**）
`handoff.md` 里的 "Active feedback" 区块我自动维护。你只管吐槽，改完自动划掉。

**默认走 C**——你不需要管"记到哪里"，我兜底。

## 验证我改的对不对

| 方法 | 何时用 |
| --- | --- |
| **看 `git diff HEAD~1`** | 我说"已改"后必看 |
| **跑 typecheck + vitest** | 我已经自动跑过，结果贴在 commit message 里 |
| **浏览器手动点** | 最快真实验证（你本地 5173） |
| **让我 `computer-use` 截图** | 我自己改完自己截一张给你对比 |

## 一次性"端到端反馈工具" 的市场现状

> ⚠️ 2026-08-28 调研：**没有完美的端到端工具**（截图 → 直接到 AI agent 改代码 → 刷新看效果）。

**已有的（各有缺）**：
- **Marker.io** / **BugHerd** / **Usersnap** — 点元素 → 自动截图+selector+发 Linear。**不能直接给 AI**
- **Loom** — 录屏 30 秒。**vision API 没普遍集成**
- **FullStory / LogRocket** — session replay。**录的是你 session，给 AI 还是要手动**
- **Sentry** — 自动捕获前端报错。**只管 bug，不管 UX 反馈**

**为什么没人做**：
- AI agent 时代才有的需求（2024+）
- 现有工具都假设"反馈 → 人类 triage → 人类派活"
- "反馈直接进 AI 上下文" 是 2025+ 才开始的产品形态

**你产品能演化进去**：
```
[点页面元素] → 浏览器插件捕获 selector+截图+鼠标位置
  → POST /api/feedback → agent-world 起"反馈处理"产线
    - 节点 1：分析截图
    - 节点 2：定位代码（grep / codegraph）
    - 节点 3：改 + 测
    - 节点 4：通知
  → 浏览器刷新
```
1-2 天能搭（浏览器插件 + 一条产线）。

## 推荐的日常工作流（3 步，10 分钟）

```
1. 打开 5173 找 3 个不爽的
2. 一次截图 3 张发我
3. 我一次会话：
   - 定位 3 处代码
   - 改 + 测
   - 给你 3 个独立 commit
4. 你 cp -r /tmp/aw.git .git 同步 + 浏览器刷新
```

**全程你只发 3 张图 + 看 diff**。

## 反模式（不要这么做）

| 反模式 | 为什么不行 |
| --- | --- |
| 长段文字描述 UI 问题 | 描述往往跑偏，截图能秒懂 |
| 反复说"还是不对"（不带新截图） | 我不知道你看到啥，无法定位 |
| 同一 bug 拆成多个 commit 派给我 | 我会迷失在"哪个是同一个" |
| 不验证就合并我的 commit | 信任是好的，diff 看 30 秒值得 |

## 给我 prompt 的最佳模板

```text
[问题截图 + 1 句 6 字标签]
[严重度（可选）]
[是否需要 computer-use 看（可选）]
```

例：
```text
[图：toolbar 下拉浮层]
"浮层没飘起来"
P1
```
