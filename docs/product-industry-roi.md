# 行业 ROI 评估：多 agent 流水编排的切入方向

> 创建：2026-09-04。评估各行业方向引入多 agent 自动化流水编排的 ROI，为「新功能 / 新模板往哪个行业投」提供决策基线。
>
> **结论基线**：专业服务（法律合规 + 财务审计）是 ROI 与 agent-world 现有能力匹配度的**交集最优**；电商/内容营销已深耕，边际递减。

## 一、评估框架

```
ROI = 人力成本节省 ÷ (所需新功能投入 + 容错成本)
```

叠加 agent-world 现有能力匹配度（29 种节点 + 电商 F1–F10 已打的地基能否直接复用）。

四个驱动因子：

| 因子 | 含义 | 对 ROI 的影响 |
|---|---|---|
| 人力成本 | 目标行业时薪 × 重复性脑力劳动占比 | 越高 ROI 越高 |
| 可自动化程度 | 确定性规则占比（可交给 code/table）vs 需要模型判断 | 确定性越高、幻觉风险越低 |
| 容错成本 | 出错代价能否接受，能否 human-in-loop 兜底 | 越低越敢上 |
| 数据 / 合规壁垒 | 数据可得性、资质要求、合规风险 | 越低越容易起步 |

## 二、行业排序（从高到低）

| 排名 | 行业方向 | ROI 驱动 | agent-world 匹配度 | 要补的新功能 / 短板 |
|---|---|---|---|---|
| 1 | **专业服务：法律合规 + 财务审计** | 时薪最高（律师/审计/法务），文书重复度极高，产出可结构化 | **极高**——合同审查、费用报销初审、证据清单、compliance 节点、fileParse/OCR/table 全套已就绪 | 几乎零新功能，补几个垂直模板即可 |
| 2 | **电商 / 内容营销** | 内容生产成本高、量级大、直接挂钩 GMV/ROI | **极高**——F1–F10 已闭环 | 已深耕，边际递减；再加是广度而非地基 |
| 3 | **客服 / 工单自动化** | 量大、24/7、替代人力直观 | **高**——客服模板 + human 节点 + 审核队列齐备 | 缺多轮对话记忆/知识库检索（MemoryBackend 未做） |
| 4 | **市场调研 / 情报聚合** | 多源搜集是多 agent 流水强项，调研耗时高 | **中高**——HTTP/search/map/loop/parallel 都在 | 搜索源硬瓶颈（DDG 反爬、需付费 key）；ROI 难量化 |
| 5 | **软件开发辅助（代码审查/测试/文档）** | 开发者薪资高、数据（GitHub）可得 | **中**——有代码审查模板 | 竞品红海（Copilot/Cursor/Devin），通用编排平台非最优载体 |
| 6 | **招聘 / HR** | 简历筛选/JD 生成量大 | **中**——OCR/table/branch 能兜底 | 需结构化简历解析、人才库数据实体 |
| 7 | **金融投研 / 医疗理赔** | ROI 本身极高 | **低** | 合规/数据/资质壁垒重、容错成本极高，需大量新功能 |
| 8 | **政务 / 公共服务** | 低 | 低 | 预算周期长、合规重 |

## 三、核心判断：为什么押「专业服务（法律 + 财务）」

1. **ROI 最高**：律师/审计时薪是客服的 5–10 倍；合同审查、发票对账的人工成本极高，而这类工作的**确定性规则占比高**（条款比对、金额校验、异常筛查），正是 agent-world 擅长的「确定性交给 code/table、判断交给模型、风险交给 human」结构。
2. **几乎零新功能**：现有 `fileParse`（PDF/DOCX/PPTX）+ `OCR` + `table` + `compliance` + `human` + `gate` 已能直接拼出合同审查、报销初审、证据清单、尽调清单——**前三个模板已经真实跑通**（狗粮验证）。这是「造场景模板」，不是「造能力」，边际成本极低。
3. **容错可接受**：专业服务天然有「人最终签字」环节，`human` 节点 + 审核队列（F2）正好兜住「agent 出初稿、人做终审」的分工，不必赌全自动。

**反而不建议现在碰**：

- 客服（第 3）卡在 **MemoryBackend 未做**——没有多轮记忆/知识库检索，客服 agent 只能做一次性分类回复，做不深。
- 金融/医疗（第 7）合规壁垒重，属阶段 5 商业化范畴，现在碰是过度设计。

## 四、专业服务垂直模板候选清单

现有覆盖（仅 3 个模板）：合同审查助手、证据清单整理、费用报销初审。共同点：单文件输入 + 确定性规则（code/table）+ 结构化清单输出 + human 把关——正是现成能力最匹配的形态。

### 第一档：现有能力几乎零成本覆盖（建议先做）

| 候选 | 方向 | 核心结构 | ROI 驱动 | 需补 |
|---|---|---|---|---|
| **银行流水对账** | 财务审计 | 双方流水 → table 双向比对 → code 差异规则 → 差异清单 | 财务每月对账刚需，纯确定性，错漏代价高 | 无 |
| **批量合同审查** | 法律合规 | 多份合同 → fileParse → 逐份风险清单 → table 汇总 | 律师一次性审 N 份同类合同的痛点 | 无（fileParse 单文档，用循环/多车间兜） |
| **隐私政策/用户协议合规** | 法律合规 | 政策文件 → fileParse → 合规条款缺失检查 → 整改清单 | 监管趋严，PII 披露/同意条款是硬要求 | 无（复用 compliance 节点） |
| **发票批量 OCR + 台账** | 财务审计 | 发票图 → OCR → 字段结构化 → table 台账 | 报销/记账前置，量大 | 无（复用 scan-ocr 的 OCR 链路） |

### 第二档：需补少量能力，ROI 高但非零成本

| 候选 | 方向 | 关键缺口 |
|---|---|---|
| **尽调清单**（并购/投资尽调） | 法律 | fileParse 现只解析单文档，多文件聚合是瓶颈（deferred 已登记） |
| **审计抽样 + 底稿生成** | 财务审计 | table 抽样规则能写，底稿模板格式需定 |
| **判决书摘要 / 类案检索** | 法律 | 需法律数据库/检索源，同 search 节点的反爬/付费源瓶颈 |

### 第三档：合规/资质壁垒重，缓做

| 候选 | 方向 | 卡点 |
|---|---|---|
| 发票验真 | 财务 | 需税务查验 API 资质 |
| 税务申报底稿 | 财务 | 需税务系统/规则库对接 |

## 五、建议切入点

**从「银行流水对账」切入**：

1. **纯确定性、零模型幻觉风险**：对账本质是 `table` 双向 JOIN + `code` 差异规则，不依赖 LLM 判断，出错代价（漏对一笔）却很高，「机器做、人复核」分工最干净。
2. **复现频率最高**：报销是偶尔一次，对账是**每月**一次，模板复用价值最大。
3. **零新功能**：`table`（排序/空值沉底已修）+ `code`（规则校验）+ `gate`（质检）直接拼，连 fileParse 都不需要（CSV/表格投料即可）。

「批量合同审查」和「隐私政策合规」紧随其后，都吃现有 fileParse + compliance + human 的老本。
