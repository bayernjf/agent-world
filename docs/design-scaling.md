# 规模化与企业级架构方案（Scaling & Enterprise Architecture）

> 状态：**方案设计（2026-09-07 起草，待评审，未实施）**。
> 定位：针对 agent-world 的**实际情况**，回答「分布式 / 高可用 / 高并发 / 大数据量 / 托管 / 数据处理 / 合规」要不要做、何时做、怎么做。
> 原则：**只做 agent-world 真正需要的，不因"提到过"就全做。** 每项先给判断（必须 / 视形态 / 大概率不需要），再给方案。
> 创建：2026-09-07

---

## 0. 关键取舍判断（先读这节，再决定要不要看后面）

### 0.1 agent-world 的实际情况（判断依据）

| 事实 | 含义 |
|---|---|
| 单用户（owner）为主，M3 计划小规模 | 不是互联网级并发产品 |
| AI 产线编排：负载是「少量但耗时 + 高成本」的 AI 任务 | 瓶颈是**成本与沙箱执行**，不是并发请求数 |
| 单机 SQLite + systemd，自托管形态 | 数据在用户自己机器上 |
| 成本敏感（按 token 计费） | 财务风险真实存在 |

### 0.2 产品形态决策（2026-09-07 已定：自托管 + SaaS 都做，先自托管）

**决策**：自托管与多租户 SaaS **两条路都走**，按「哪个方便先来哪个」——**先自托管（当前，最方便），后 SaaS（后续）**。

| 形态 | 时机 | 对企业级能力的影响 |
|---|---|---|
| **A 自托管**（每用户自己部署，类似 n8n / Dify 开源版） | **先**（当前） | SQLite 够、单机够，**不需要**分布式/HA/合规 |
| **B 多租户 SaaS**（官方托管，类似 Dify Cloud） | **后**（后续） | **需要** PG、多副本、合规、HA |

**含义**：「视形态而定」的能力不是"可能永远不做"，而是**有时间线**——自托管阶段不做，进入 SaaS 阶段再做。落地路线见 §5。

### 0.3 三类判断（一句话总结）

| 判断 | 能力 | 理由 |
|---|---|---|
| ✅ **必须做**（与形态无关） | 成本硬熔断、备份恢复演练、health 探针、对象存储 | 财务风险 / 数据安全，任何形态都要 |
| 🔀 **视阶段而定**（自托管不做，SaaS 做） | SQLite→PG、分布式、HA、高并发、合规、托管 | 取决于自托管 A（先）vs SaaS B（后） |
| ❌ **大概率不需要** | k8s 自建、分库分表、高并发全套（Redis/队列/水平扩展） | agent-world 不是高并发产品 |

## 1. 必须做的（与形态无关，P0 可立即做）

这几项不取决于产品形态，是 agent-world 任何形态下的硬需求：

| 能力 | 为什么必须 | 方案要点 |
|---|---|---|
| **成本硬熔断** | AI 按 token 计费，死循环/被刷/攻破可致账单失控 | 月度预算超限硬停新 run（现有 `monthlyBudgetUsd` 只有 warn） |
| **备份恢复演练** | 备份已做但从没验证能恢复 | 定期在干净目录恢复 + 启动验证，明确 RTO/RPO |
| **health 自述探针** | 三环境状态检测的最低门槛 | 升级 `/api/health` 报 env/branch/commit + DB/密钥就绪 |
| **artifacts 迁对象存储** | 图片/视频/音频二进制会持续占盘，这是**唯一确定的规模化需求** | 从本地盘迁 S3/OSS/COS，DB 存 key |

> 详细方案见 [production-ops.md](production-ops.md)（探针/熔断）与 [engineering-blueprint.md](engineering-blueprint.md) 域 7（数据）。

## 2. 视阶段而定的（自托管阶段不做，SaaS 阶段做）

这些能力**做不做，取决于形态阶段**：自托管（先）不需要，SaaS（后）需要。落地按 §5 时间线排期，自托管阶段不动工。

> 数据层多租户模型（tenant / user / 资源 / 计费 + 向后兼容演进）见 [design-multitenancy.md](design-multitenancy.md)。

### 2.1 SQLite → PostgreSQL

- **形态 A（自托管）**：SQLite **长期够用**（单用户、数据量有限），不迁。
- **形态 B（SaaS）**：**必须迁**（多租户 + 并发写 + 连接池）。
- 触发条件：进入 SaaS 阶段（自托管跑通后）。
- 落地：`db.ts` 已有访问抽象，迁 PG = 换 driver + SQL 方言适配；保留 SQLite 驱动供自托管/本地 dev。
- **事件流存储（2026-09-07 评审）**：`events` 表是数据量增长第一来源。策略定为**热库 + 冷归档**——近 N 月 events 留在库（支持回放），老的按 run 归档到对象存储（`runs.snapshot` 已存完整快照，归档不影响恢复）。触发条件：events 表成为查询/存储瓶颈时再做，现在不提前。

### 2.2 分布式 / 高可用（多副本）

- **形态 A**：单机够，不需要。云托管自带的"故障自动拉起"已是够用的 HA。
- **形态 B**：需要无状态化 + 多副本 + 负载均衡。
- 触发条件：多租户 SaaS + 有 SLA 承诺。

> **无状态化的真实范围（2026-09-07 评审）**：多副本**不需要把 run 状态全部外置**，只需两件事：
> 1. **调度器分布式锁**（cron 触发器多实例重复触发 → §4.5 的 PG advisory lock）；
> 2. **SSE 粘性会话**（同一 run 的 SSE 固定路由到执行它的实例）。**方向（2026-09-07 评审拍板）：粘性会话起步**——run 执行本身是单实例长任务、状态在内存，粘性最贴合；事件总线只在「实例频繁扩缩容、粘性失效」时才升级。
> 其余（AsyncLocalStorage 单请求内上下文）无需改造。

### 2.3 高并发

- **判断：agent-world 大概率到不了高并发**——它是「少量长任务」型负载，瓶颈是 AI 成本，不是 QPS。
- 唯一可能需要的：入口限流（防滥用）+ 沙箱执行隔离（CPU 密集），两者 P0/P1 已覆盖。
- 全套高并发（Redis 缓存 / 消息队列 / 水平扩展）：**除非变成 SaaS 且并发上来，否则不做**。

### 2.4 合规（SOC2 / ISO27001 / 个保法）

- **形态 A（自托管）**：数据在用户机器，**官方不碰数据，合规责任在用户侧**，官方无需 SOC2。
- **形态 B（SaaS）**：托管用户数据，**必须**合规（审计防篡改、数据删除权、密钥 KMS、MFA）。
- 触发条件：做 SaaS 且接入企业客户。

### 2.5 托管方案

- **形态 A**：用户自托管，官方只需发**发布包 + 部署文档**（runbook 已有）。
- **形态 B**：官方云托管（容器服务 + 托管 PG + 对象存储 + CDN），见 [production-ops.md §4](production-ops.md)。

## 3. 大概率不需要（明确判断，除非形态突变）

| 能力 | 判断 | 理由 |
|---|---|---|
| **自建 k8s** | ❌ 大概率永远不需要 | 形态 B 也用云容器服务（免运维 k8s）；自建集群需专业运维团队，agent-world 没有也不会有 |
| **分库分表** | ❌ 大概率永远不需要 | 单用户数据量有限；即便 SaaS，事件流/artifacts 外置对象存储即可，轮不到分库分表 |
| **高并发全套** | ❌ 大概率不需要 | 见 §2.3，负载特征不支持 |
| **微服务拆分** | ❌ 不需要 | 单体 + 模块化（monorepo）足够，拆分是纯成本 |

## 4. 详细方案（评审用，仅覆盖"必须做"与"视形态"项）

> 以下给「到点后怎么做」的具体方案，供评审；**不代表现在做**。

### 4.1 成本硬熔断（✅ 必须）

- 现状：`monthlyBudgetUsd` 仅 80%/100% warn（emit 事件，不拦截）。
- 方案：`startRun` 入口检查 `monthSpentUsd >= monthlyBudgetUsd` → 拒绝新 run（HTTP 429），owner 可在 Settings 调高预算或关 0 放行。
- 测试：超预算拒绝 / 未超放行 / 预算禁用(0)不熔断。

> **成本两层（2026-09-07 评审拍板）**：成本控制分两层，**不要用一个变量同时表达**：
> - **平台成本护栏**（本节 `monthlyBudgetUsd` 硬停）：owner/平台级，防账单爆炸（bug 死循环、被刷）——自托管下 owner=唯一用户，预算=配额，两层合一。
> - **租户订阅配额**（[design-monetization.md](design-monetization.md) 的 `enforceSubscription`）：租户级，防免费白嫖/超用额度——仅 SaaS 阶段启用。
> 自托管阶段只落「平台成本护栏」这一层；SaaS 阶段两层分离（每租户配额 + 平台总护栏）。

### 4.2 备份恢复演练（✅ 必须）

- 现状：cron 每日 02:30 备份（SQLite 快照），**从未演练恢复**。
- 方案：定期在干净目录 `cp -a 备份 → 恢复目录` + 启动 server 验证 DB 可读、产线/run 可见；记录 RTO/RPO。
- **RTO/RPO 目标（2026-09-07 评审拍板）**：自托管阶段 RPO=24h（每日备份，最多丢一天）、RTO=30min（从发现到恢复，单机 SQLite 恢复=拷回+重启）。演练按此验收；SaaS 阶段（云托管 PG）再收紧到 RPO≈0 / RTO 分钟级。

### 4.3 artifacts 迁对象存储（✅ 必须，唯一确定规模化需求）

- 现状：`local` 存储，二进制落本地盘。
- 方案：ArtifactStore 增加 `s3` 后端（S3 兼容 API），`saveBinary` 上传对象存储、DB 存 key；`readArtifact` 走预签名 URL。**与 PG 迁移解耦，可提前独立做**。

### 4.4 SQLite → PG（🔀 视形态）

- 迁移方式：小库一次性 ETL（停机导出→转换→导入）；大库双写渐进。
- 兼容：`db.ts` 抽象已具备；保留 SQLite 供自托管/本地 dev。

### 4.5 分布式锁（🔀 视形态，多实例前置）

- 场景：cron 触发器 / 定时任务在多实例下重复触发。
- 方案（2026-09-07 评审拍板）：**PG advisory lock**（迁 PG 后零额外依赖、简单可靠）。Redis 只在「真需要缓存/队列削峰」时才引入，届时锁再跟 Redis 统一——顺序是**先 PG advisory lock，不提前上 Redis**。

## 5. 落地路线（基于判断，非"全做"）

| 阶段 | 做什么 | 触发条件 |
|---|---|---|
| **P0（现在可做）** | 成本硬熔断、备份恢复演练、health 探针、gitleaks、artifacts 迁对象存储 | 与形态无关，已到点 |
| **阶段 1（自托管对外时）** | 云托管 + CI/CD + TLS + 可观测 + 供应链扫描 | 自托管要对外（M3 前） |
| **阶段 2（做 SaaS 时）** | SQLite→PG + 多副本 + 分布式锁 + 合规 | 自托管跑通后启动 SaaS |
| **不做** | k8s 自建、分库分表、高并发全套、微服务 | 大概率永不触发 |
