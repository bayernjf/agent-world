# RTS 宏观上帝视角设计总览（design-rts-overview）

> 定位：把「单张产线的等距 3D 视图」升级为「名下所有产线同屏运转的工业园区」的产品形态与落地路径设计。
>
> 状态：**方向立项 / P3；阶段 A（平面运营工作台）已于 2026-09-10 全部完成上线（PR #239 `514d18a`），阶段 B/C 仍为未实施草案**（PRODUCT_STRATEGY §七定性为后差异化留存手段）。创建：2026-09-10。
>
> 约定：延续「工业沙盘」本体论（见 [design-glossary.md](design-glossary.md)）——本体是工厂，不是游戏皮肤；服务器算真实业务，浏览器本地 GPU 渲染，不烧服务器算力（PRODUCT_STRATEGY §七）。

## 一、定位与一句话定义

- **L1 微观 3D（已建成，见 [design-canvas-isometric.md](design-canvas-isometric.md)）**：钻进**一座工厂内部**——一张产线图的节点、管道、卡车、状态灯，用于查看与微调布局。
- **L0 宏观 RTS（本文，待建）**：拉开到**俯瞰整个工业园区**——用户名下所有产线在同一张等距大地图上同时活着：哪座厂在开工、哪座在等人审批、哪座失败、产物往哪流、未来几点哪座厂开工，一屏看全；点一座厂平滑推近到 L1。
- 类比：帝国时代 3 / 红警的基地视角——多座建筑同屏运转、资源在建筑间流动、点建筑进入操作；**游戏在本地运行、真实数据在服务器**，浏览器就是本地客户端。

**解决的核心问题：多产线运营的「全局失明」。** 产线一多（当前 M1 回采已挂 4 条），只能靠顶部产线下拉逐个切进去看状态，没有「一眼看全局」的界面。L0 把运行 / 待办 / 失败 / 排期 / 成本压进一屏，完成从「单条产线编辑器（工具）」到「运营指挥中心（工作台）」的跃迁。

## 三、形态：三层连续缩放世界

### 3.1 L0 工业园区（待建）

每条产线 = 一座工厂建筑，按节点类别 / 业务线分区摆放（复用 L1 五组配色语义），同屏实时运转。承载六类信息（详见 §四）。L0 上可做轻操作（§五），重编辑仍下钻。

### 3.2 L1 单厂内部（已建成）

现有等距 3D：29 种造型、圆管管道、卡车、LED、拖节点布局。L0 钻取后的落点。

### 3.3 L2 节点配置（已有）

Inspector（模型 / prompt / 重试 / 成本），钻取终点。

### 3.4 L0↔L1 连续钻取（关键交互）

- **不是页面跳转，是相机连续运动**：L0 点厂 → 正交相机平滑推近 + 场景从「宏观低模」过渡到「该厂 L1 精细场景」；反向逐级拉远。
- 保留 L1 已有的视角记忆（yaw/pan persist），钻取回来不丢上下文。
- 降级路径：连续过渡实现成本高时，阶段 B 先用「点击切场景 + 250ms 淡切」（L1 已有交叉淡切机制可复用），连续 zoom 留到阶段 C。

## 五、宏观轻操作（不进图就能做的事）

- **审批**：点待办货车 → 审批卡（通过 / 驳回 / 编辑），复用 `POST /api/reviews/decide` 内核，不进 run 详情。
- **重试 / 暂停**：失败厂「重试该节点 / 重跑」、cron 厂「暂停 / 恢复排程」。
- **改期**：拖排期芯片改 cron / content_plan 时间。
- **钻取**：点工厂本体进入 L1；点 L1 节点进入 L2。
- 边界：**宏观只做运营操作与查看，不做图结构编辑**（增删节点 / 连线仍在 L1/L2），避免在低模视图里引入高风险编辑。

## 六、技术架构原则

1. **算力分工（PRODUCT_STRATEGY §七）**：服务器只算业务状态（run / 成本 / 排期），经 SSE（必要时 WebSocket）推送；所有动画、相机、几何在用户浏览器 GPU 本地渲染，服务器不承担渲染成本。
2. **复用 L1 基建**：`iso3d-shapes`（造型 / 材质 / LED 配色）、相机与 raycast、坐标映射纯函数（`iso3d.ts`）尽量直接复用；L0 是「多实例场景编排」，不是第二套渲染器。
3. **LOD 是性能硬要求**：同屏 N 座精细工厂 GPU 扛不住。L0 用低模 / billboard（盒体 + 类别色 + 状态灯 + 图标），只有被钻取的厂加载 L1 精细几何；视口外工厂冻结 rAF / 降帧。
4. **宏观自动布局**：跨图分区布局算法（按业务线 / 类别聚簇，类 BFS 分层），新增产线自动入位，用户可手动挪动并持久化（类比 L1 的 moveNode，但作用在「园区地图」层）。
5. **数据层走 db.ts 抽象**：新增跨产线聚合接口（全局 run 状态、跨厂物流视图）必须在 `packages/server/src/db.ts` 加方法，禁止裸 SQL（AGENTS.md 数据访问规约），兼容 SQLite / PostgreSQL 双轨。
6. **包体积**：L0 独立 chunk + `React.lazy`（沿用 L1 策略），2D / 单厂用户不加载宏观代码。
7. **UI 规约**：所有可见文案走 i18n `t()`、颜色间距走 CSS 变量 / 既有语义色（AGENTS.md），工厂语义色复用 L1 既有调色板。

## 七、价值（为什么值得做，按强度排序）

1. **治全局失明（真实功能价值）**：多产线状态 / 待办 / 失败 / 成本一屏掌控，是规模化使用的刚需界面，而非装饰。
2. **差异化（竞品空白）**：n8n / Dify / Coze / Flowise 全是 2D 节点图 + 列表，没有「活的运营沙盘」；RTS 是工业沙盘本体论的自然终点，demo 录屏自带记忆点与传播性。
3. **游戏化留存与续费**：看着 AI 工厂 7×24 自动出货，是「自动化在替我赚钱」的具身体感；自动化工具的续费关键是让用户持续感知资产在增值，而不是面对一堆 run 记录。
4. **商业化协同**：工厂数量天然可视化套餐档位（Free 1 座 / Pro N 座 / Team M 座）；全局电费滚动让 BYOK 与订阅价值可感知，升级动机长在界面上（与 [design-monetization.md](design-monetization.md) 套餐设计呼应）。
5. **技术杠杆高**：L1 渲染引擎、SSE 状态、cron、halted、成本计量、F2/F6/F8/F9 全部已存在，L0 是拼装与聚合，不是从零造。

## 八、代价、风险与边界

- **LOD 与性能**：同屏多厂是全新工程问题，必须先低模后精细，否则中端设备掉帧。
- **宏观布局算法**：跨图自动分区布局无现成基础，需要单独设计与测试。
- **连续相机过渡**：L0↔L1 场景切换的相机运动与资源加载时序有交互复杂度（阶段 B 可先用淡切降级）。
- **跨厂物流依赖关系普及**：产线间目前基本隔离，「产物流转」要有普遍的跨产线触发 / 产物引用关系才成立，否则 L0 上只有孤立工厂。
- **价值前提 = 多产线用户**：单产线用户打开 L0 是空地图，因此本特性**依赖用户规模与人均产线数**，这也是它被定在 P3 的根本原因。
- **明确不做**：不替代 2D 编辑、不做自由视角 3D、不做服务器端渲染 / 服务端动画、不在宏观视图做图结构编辑。

## 十、时机判断（为什么是 P3）

- PRODUCT_STRATEGY §七明确：RTS 属「P3 后差异化留存手段，先做 P0–P2，别抢 MVP」。
- 当前主线：**M1 成本回采（进行中，每日体检攒数据）→ 订阅 gate → 支付商业化闭环**；L0 不抢主线资源。
- **阶段 A 是唯一可提前的部分**：平面、低成本、且能验证需求，可在 M1 等待数据的窗口期择机插入。
- **重启触发条件**（同步登记 [deferred-items.md](deferred-items.md) 商业化线）：商业化闭环跑通 **且** 出现真实多产线运营场景（参考阈值：活跃用户人均 ≥3 条产线，或用户主动反馈「产线多看不过来」）。
